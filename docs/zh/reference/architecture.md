# RFC 0001：模块化核心与 Provider 契约

| 字段 | 内容 |
| --- | --- |
| 状态 | 已接受 |
| 接受日期 | 2026-09-04 |
| 范围 | 内部架构；不改变 CLI 或 Profile 格式 |

## 摘要

Winenv 继续定位为有明确取舍的 Windows 环境编排层，而不是万能软件仓库或托管式环境管理平台。稳定入口 `win.ps1` 负责加载较小的内部实现文件，各软件管理器的行为则通过经过校验的 Provider 注册表调用。

本 RFC 记录后续修改必须遵守的架构。`src/` 下的文件属于内部实现，可以随版本演进；`win` 命令、已公开参数、Profile schema、状态路径和 Release 安装流程才是兼容边界。

## 背景

最初的单文件实现简化了引导和分发，但后来增长到三千多行，同时包含国际化、Profile、状态、软件发现、安装器、软件管理器与命令路由。修改一个管理器前往往需要理解大部分程序，不相关的改动也更容易冲突。

Winenv 已经具备声明式基础：Profile 表达所需能力，多个已启用 Profile 组合成最终定义，已有安装可以复用或纳入，冲突必须由本机明确选择。下一步需要让这些职责可以独立测试，而不是把 Winenv 变成通用插件市场。

## 决策

### 保留轻量、稳定的入口

`win.ps1` 只负责：

- 命令参数与别名；
- 单次调用使用的路径和状态；
- 加载内部实现文件；
- 初始化国际化和 Provider；
- 顶层命令路由与错误本地化。

入口不再包含函数实现。Release 仍然提供同一个 `win.ps1`，安装器与启动器的调用方式也完全不变。

### 分离职责

| 路径 | 职责 |
| --- | --- |
| `src/Localization.ps1` | 语言选择、消息、表格、提示与帮助 |
| `src/Core.ps1` | 原生命令执行、命令探测、前置要求与自更新 |
| `src/Profiles.ps1` | Profile 解析、快照、组合、冲突与选择 |
| `src/Inventory.ps1` | 软件候选项、实时搜索、已安装清单与纳入 |
| `src/Planning.ps1` | 复用/安装计划与安装编排 |
| `src/State.ps1` | 持久状态与迁移 |
| `src/Commands.ps1` | 健康检查、更新、卸载、清理与 Shell 集成 |
| `src/Providers/` | Provider 契约及各管理器实现 |

这些实现文件会 dot-source 到同一个调用作用域。这样可以保留 Windows PowerShell 兼容性，也能继续在测试中替换单个函数。内部模块加载时不得直接执行用户操作。

### 启动时校验 Provider

Profile 允许的每一种归属必须有且只有一个已注册 Provider。Provider 描述包含稳定名称，以及操作到处理函数的映射。如果处理函数缺失、登记了未知操作，或者 Provider 集合与 Profile 归属不一致，程序会在任何软件操作前停止。

首版契约只纳入当前已经可以安全统一的操作：

| 操作 | 输入 | 预期结果 |
| --- | --- | --- |
| `Search` | 查询文本 | 零个或多个统一格式的软件候选项 |
| `Install` | 软件声明与调用上下文 | 安装、复用，或明确展示发布者手工交接信息 |
| `Remove` | 软件声明与调用上下文 | 委托记录的软件归属方卸载 |

`winget`、`scoop` 和 `mise` 实现全部三个操作。`vendor` 只实现安装与卸载交接，不伪装成拥有可搜索的软件目录。

清单、详情、更新、纳入和计划目前仍保留管理器专用实现，直到它们的输入与结果真正可以统一。过早把名称塞进契约只会掩盖差异，而不是隔离差异。

## Provider 准入规则

只有在解决现有 Provider 无法表达的、机器级 Windows 环境职责时，才考虑新增 Provider。提案必须说明：

1. 具体用户问题，以及为何 Profile 或现有来源无法解决；
2. 搜索、安装、更新、卸载与纳入语义；
3. 提权、重启、信任、签名与回滚行为；
4. 如何处理已有安装与软件归属；
5. 长期维护成本及 Provider 不可用时的行为；
6. 每个公开操作在 PowerShell 7，以及适用时在 Windows PowerShell 5.1 下的测试。

npm、pip、cargo 等项目依赖生态不会自动成为机器级 Provider。运行时由 mise 管理，项目依赖通常继续使用项目自己的 lockfile。Windows Features 等需要提权的系统能力，在准入前必须单独完成安全设计。

当前注册表是内部机制。Winenv 不会从用户目录或 Profile 加载第三方代码，也不承诺公共插件 API。

## 兼容性不变量

模块化修改必须保留：

- `win` 命令和已公开别名；
- Profile schema 版本 1 与独立 Profile 快照；
- 停用 Profile 不卸载软件；
- 已有软件归属和纳入语义；
- 英文优先、正式支持简体中文的国际化方案；
- Windows PowerShell 语法兼容与 PowerShell 7 执行；
- 带版本的 Release ZIP、校验和、安装器与稳定启动器；
- 信任、提权与破坏性操作必须明确确认。

如需改变任一不变量，必须另写 RFC、迁移方案，并明确决定兼容性影响。

## 测试与打包

CI 会递归检查入口和所有内部 PowerShell 文件的语法与国际化覆盖。架构测试要求入口不包含函数实现、内部函数不得重复、每个实现文件只能加载一次、所有 Provider 处理函数都有效，并实际验证 Provider 分派。

Release 构建会把 `src/` 与 `win.ps1` 一起打包；全新系统安装冒烟测试会确认已安装版本包含 Provider 契约。因此内部文件和入口共享同一个带版本、带校验的更新边界。

## 非目标

本决策不会建立：

- 公共插件市场，或对内部函数的兼容承诺；
- Winenv 自己维护的万能软件索引；
- 账号服务、企业控制面、角色权限系统或 Web 后台；
- 对所有 npm、pip、cargo、Docker、WSL 或 Windows 功能的自动管理；
- 严格删除未在 Profile 中声明的软件。

团队使用仍应从放在 Git 中、可以评审的 Profile 开始。只有真实用户证明文件分发无法满足需求后，才考虑企业专用机制。

## 后续步骤

本 RFC 下的模块拆分和首版 Provider 注册表已经完成。后续按以下顺序推进：

1. 复用现有最终 Profile 与软件清单模型，提供只读 `win diff`；
2. 评估可选 lockfile，记录解析后的版本、来源和哈希，但不取代 Profile 表达的用户意图；
3. 设计 `win sync`，默认只安全地安装与修复，删除必须显式指定 prune；
4. 只有当各管理器的行为确实能统一时，才把更多操作纳入 Provider 契约；
5. 等内部契约跨多个版本保持稳定后，再讨论公共扩展接口。

## 影响

新架构会增加 Release 中的文件数量，单独下载一个裸 `win.ps1` 也不再足够；受支持的安装器本来就会下载完整、带校验的 Release。作为回报，改动范围会更小，Provider 职责更清楚，测试能够约束边界，未来声明式功能也能复用稳定核心，而不必把 Winenv 变成平台。
