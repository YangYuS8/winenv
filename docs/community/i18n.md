# Translation guide

Winenv supports English (`en-US`) and Simplified Chinese (`zh-CN`) across the CLI, installer, repository entry points, and documentation.

## Source of truth

English is canonical. It lives in:

- English literals in `win.ps1` and `install.ps1`;
- root documentation pages under `docs/`;
- root repository policy files such as `CONTRIBUTING.md`.

Simplified Chinese lives in:

- `locales/zh-CN.json` for CLI output;
- `docs/zh/` for the documentation site;
- `.zh-CN.md` policy and README counterparts.

The English resource file documents the locale schema and leaves English mappings empty because source strings are already English.

## Runtime language selection

The CLI and installer resolve language in this order:

1. explicit `-Lang` or `-Language` parameter;
2. `WINENV_LANG` environment variable;
3. persisted `language` in `%LOCALAPPDATA%\Winenv\config.json`;
4. current Windows UI culture (`zh-*` selects Chinese; everything else selects English).

Passing `auto` deliberately skips environment and stored preferences for that invocation and consults the system UI culture. `win lang auto` persists that behavior.

The documentation uses English at `/` and Chinese at `/zh/`. On a visitor's first page load, the theme follows the browser language. A manual language-menu choice is stored locally and takes priority on later visits.

## Translation rules

- Preserve command names, flags, paths, environment variables, package IDs, code, JSON keys, and log fragments.
- Prefer natural user-facing language over a word-for-word translation.
- Keep terms such as WinGet, Scoop, mise, Profile, manifest, bucket, Release, Issue, and Pull Request when translation would make cross-referencing harder.
- Translate intent consistently: `adopt` means adding a reproducible claim without reinstalling; `reuse` means an existing compatible installation satisfies the plan; `unclaimed` does not mean uninstalled.
- Do not promise safety, support, or compatibility beyond the English source.
- Update links so a Chinese page normally stays within `/zh/` and an English page stays in the root locale.

## Adding or changing messages

English CLI text is the fallback key. Add an exact entry for fixed text, a narrowly anchored regular expression for dynamic text, or a replacement only when the phrase is unambiguous. Avoid broad expressions that can translate package names or upstream output.

After changing user-facing text:

```powershell
pwsh -NoProfile -File ./scripts/test-i18n.ps1
pwsh -NoProfile -File ./scripts/test.ps1
npm run docs:build
```

The localization test validates resource JSON, language precedence, persistence, automatic culture detection, table output, and the rule that CLI host output passes through localization wrappers.

## Adding another language

A new language requires more than one JSON file. It needs a maintained CLI resource, installer messages, complete documentation locale, VitePress navigation and search labels, browser routing, automated tests, and reviewers able to keep it current. Start with a design issue that identifies long-term maintainers before implementation.
