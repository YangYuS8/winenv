# Core abstraction ablation review — 2026-09-04

[简体中文](./2026-09-04-ablation.zh-CN.md)

## Decision

Two install forwarding layers are candidates for removal: `Install-WinGetPackage` and `Install-ScoopPackage` only serve their corresponding provider entry points. Moving each body into that entry point removes two functions and ten lines without changing the provider contract. The tested variant preserved the observed behavior.

Retain provider registration validation, mise's context adapter, and package-definition copying. Their removal produced concrete contract or profile failures. Removing the separate configuration clone remains inconclusive: aliasing was demonstrated, but a user-visible regression was not.

This is an engineering record, not a new architecture RFC or a claim that the entire project has been optimized. At the time of the initial review, no runtime deletions from the experiments had been merged. The useful fault cases were retained in the existing [architecture tests](../../scripts/test-architecture.ps1); no permanent ablation framework, dependency, or CI job was added. Runtime simplifications require supported Windows verification before landing.

## Method

- Baseline: commit `b000ee2`, including the approved agent instructions; runtime code is unchanged from `c8f40c5`.
- Environment: Linux x64, PowerShell 7.6.5, fresh process and isolated temporary state for each run. Native install calls in the additional probes were mocked. The existing suite uses mocks and dry runs. No actual user software was installed or removed by these tests.
- One intervention per source copy; variants were not stacked. Original tests were kept unchanged for the first comparison.
- Each copy ran `pwsh -NoProfile -File ./scripts/test.ps1` and 17 additional checks: four WinGet/Scoop install argument cases, two native-error propagation cases, three mise context cases, six registration faults, repeated profile composition, and one configuration-aliasing probe.
- Six baseline/variant suite runs and 102 supplemental check executions completed. Outcomes are functional observations, not timing benchmarks or proof of equivalence outside the tested cases.

## Results

| Variant | Exact intervention | Original suite | Supplemental checks | Interpretation |
| --- | --- | --- | --- | --- |
| Baseline | None | Pass | 17/17 | Control |
| Pure install forwarding | Rename the WinGet/Scoop helper to its existing `Invoke-…ProviderInstall` entry, accept the same `Package, Context` parameters, and delete the old forwarding entry | Pass | 17/17 | Small, evidence-backed simplification candidate |
| Registration validation | Remove the owner, duplicate, empty-operation, operation-name, handler-existence, and registry/owner-set checks; preserve registry storage and dispatch | Pass | 11/17 | Six invalid registrations stop being rejected; retain checks |

| Package copy/filter | Replace `Copy-PackageDefinition`'s body with `return $Package` | Fail | 16/17 | Computed ownership fields leak into input and adopted snapshots; retain isolation/filtering |
| Configuration clone | Replace `Copy-WinenvConfig`'s body with `return $Config` | Pass | 16/17 | Only the aliasing probe fails; necessity remains unproven at the command level |

### Why passing the old suite was insufficient

Removing registration validation still allowed normal search/install/remove dispatch, so the original suite passed. Fault injection demonstrated acceptance of an unknown provider, a duplicate registration, an empty operation map, an unknown operation, a missing handler, and an owner with no implementation. These checks detect internal contract mistakes; this experiment does not claim an external plugin vulnerability.

Removing mise's adapter also passed the original suite. A direct handler probe with `ProfileManagedMise = $true` changed the captured native arguments from `install node@26` to `use --global node@26`. That is a real ownership/configuration difference, not merely a renamed helper.

Package copying is not just an extra function call. Without its field filtering and separate result object, the original adoption test failed schema validation at `/packages/0/_identity`. Reusing a profile override also failed validation because `_identity`, `_refs`, `_claims`, `_defaultSelected`, `_profileGroups`, and `_runtime` had been added to the input object.

The configuration-clone probe has a weaker interpretation. It changes a nested property on a proposed configuration and observes whether the original object changes. A no-copy implementation fails by definition. Since the tested commands still passed, this alone is **not** evidence that the clone is required by a real user flow. Do not promote this probe into a test that forbids a future valid refactor. Keep the current one-line clone pending a focused call-site/rollback investigation; no performance benefit was measured.

## Regression checks retained

The architecture test now covers the 16 behavioral/contract scenarios, without requiring the two forwarding helper names or a particular configuration-copy implementation. The aliasing-only probe was deliberately excluded.

The strengthened test was run against all six copies:

- Baseline and pure-forwarding removal passed.
- Removed registration checks, missing mise context, and missing package copying each failed for the intended reason.
- Configuration-clone removal passed, reflecting the unresolved command-level question.

This distinguishes useful tests from assertions that merely freeze the existing implementation.

## Reproducing and extending the review

1. Create isolated source copies at `b000ee2`; do not modify an installed Winenv directory or real package-manager configuration.
2. Apply one intervention from the table to each copy. Keep an unchanged control.
3. Run the baseline version of `scripts/test.ps1` in each copy.
4. Copy this review's strengthened `scripts/test-architecture.ps1` into each copy and rerun it. The unchanged version of the production runtime must pass first.
5. If investigating configuration cloning, compare a nested edit on `Copy-WinenvConfig`'s result with the original configuration, then look for an actual command, cancellation, retry, or rollback consequence. An aliasing assertion alone is insufficient.
6. Before accepting a runtime simplification, run the full checks on supported Windows, including `powershell.exe -NoProfile -File ./scripts/test-windows-powershell.ps1`, and review source qualification, error propagation, profile ownership, and release packaging.

Windows integration and Windows PowerShell 5.1 were not tested in this Linux experiment. Remaining modules, documentation infrastructure, and release automation were inspected for context but not ablated. The validated registry and thin-entry architecture remain the accepted design.

## Approved implementation and Windows CI

The maintainer approved removing only the two pure install forwarding layers. Commit `ebde85e` implements that scope; the provider contract, validation, mise context, and profile logic are unchanged. [CI run 33851373334](https://github.com/YangYuS8/winenv/actions/runs/33851373334) passed for that exact revision: the full PowerShell 7 suite and Windows PowerShell 5.1 compatibility checks on Windows Server 2025, plus documentation checks, build, and all 14 browser tests. This closes the Windows CI gap for the refactor; it is not a claim of a real Windows 11 package-installation trial.
